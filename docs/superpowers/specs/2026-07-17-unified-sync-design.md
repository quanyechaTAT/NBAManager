# 统一自动、手动与登录补偿同步设计

## 1. 背景与目标

数据管理中心的手动同步用于在自动更新不及时、自动任务失败或系统停机错过调度时立即刷新数据。手动同步不是另一套同步实现，而是自动同步在当前时刻的显式触发版本。

本设计的核心目标：

- 自动、手动和登录补偿对同一模块执行完全相同的数据范围、Provider 参数、超时、质量门、入库逻辑和缓存刷新。
- 触发来源只影响任务元数据，不影响同步结果。
- 所有真实执行均有持久任务记录、真实进度、明确终态和可靠取消能力。
- 管理员登录后自动补跑系统停机期间错过的调度，且不阻塞登录。
- 全量同步中单个模块失败不阻断后续模块。

## 2. 非目标

- 手动同步不扩大自动任务的数据范围。
- 不为手动同步提供独立 Provider、参数或质量标准。
- 不逐次回放停机期间错过的每一个调度周期。
- 去重清理等维护任务不作为可手动触发的数据模块。
- 本次设计不引入外部消息队列。

## 3. 总体架构

所有触发来源统一提交 `SyncCommand`：

```text
@Scheduled ───────────────┐
管理员手动操作 ───────────┼─> SyncCoordinator.submit(command)
管理员登录补偿检查 ───────┘              │
                                        ▼
                              SyncDefinitionRegistry
                                        │
                                        ▼
                                  ModuleSyncWorker
                                        │
                                        ▼
                         Provider -> 质量门 -> 事务入库 -> 缓存
```

### 3.1 统一提交入口

- `submitScheduled(module)` 提交 `SCHEDULED` 任务。
- `submitManual(module, requestedBy)` 提交 `MANUAL` 任务。
- `submitLoginCatchup(module, requestedBy)` 提交 `LOGIN_CATCHUP` 任务。
- `submitFullSync(triggerType, requestedBy)` 提交全量父任务。
- 原有 `@Scheduled` 方法只负责提交任务，不再直接调用业务 Service 或 Worker。

### 3.2 模块定义注册表

`SyncDefinitionRegistry` 是模块执行策略的唯一来源，每个定义包含：

- 模块标识及显示名称。
- 对应的 `ModuleSyncWorker`。
- 自动调度表达式或固定周期。
- 使用的超时类别。
- 全量同步中的执行顺序。
- 用于补偿判断的最近应执行时间计算规则。

Worker 是实际同步的唯一入口。触发方不得覆盖 Worker 的数据范围、脚本参数、Provider 或质量门。

## 4. 任务模型

### 4.1 SyncJob

任务记录包含：

- `module`
- `triggerType`: `SCHEDULED`、`MANUAL`、`LOGIN_CATCHUP`
- `requestedBy`
- `status`
- `progress`
- `stage`
- `heartbeatAt`
- `cancelRequested`
- `fetchedCount`、`insertedCount`、`updatedCount`、`skippedCount`
- `source`
- `errorCode`、`errorMessage`
- `createdAt`、`startedAt`、`finishedAt`

### 4.2 SyncJobStep

`FULL_SYNC` 使用父 `SyncJob` 和多个 `SyncJobStep`。每个步骤对应一个模块，保存模块状态、进度、统计、错误和起止时间。步骤由父任务顺序执行，不作为独立队列任务重复抢锁。

父任务根据步骤结果汇总：

- 所有步骤成功：`SUCCESS`
- 至少一个步骤失败或部分失败：`PARTIAL_FAILED`
- 用户取消：`CANCELLED`
- 锁丢失或不可恢复的编排异常：`FAILED`

## 5. 提交、去重与并发

### 5.1 同模块活动任务

活动状态包括 `QUEUED`、`RUNNING`、`CANCELLING`。

- 自动或登录补偿触发遇到同模块活动任务时直接去重，不创建伪任务。
- 手动触发遇到同模块活动任务时返回现有任务，响应中 `reused=true`。
- 前端关联该任务的真实进度并显示实际触发来源。
- 管理员可取消关联到的自动任务；任务达到 `CANCELLED` 后，重新点击同步才创建新的手动任务。

### 5.2 普通模块并发

- 同一模块跨实例互斥。
- 不同模块可并行，但受统一任务线程池并发数限制。
- Redis 锁负责跨实例互斥，数据库活动任务记录负责展示、恢复与二次校验。

### 5.3 全量同步

- `FULL_SYNC` 是全局独占任务。
- 创建全量任务前必须没有普通活动任务，否则返回冲突模块列表。
- 全量任务运行时，模块手动按钮关联到对应全量步骤，不重复创建任务。
- 单步骤失败后继续执行后续步骤。
- 失败步骤可在全量结束后通过模块按钮单独重试。

## 6. 执行生命周期

1. Coordinator 校验模块并原子检查活动任务。
2. 获取任务锁并创建 `QUEUED` 记录。
3. 执行器领取任务，写入 `RUNNING` 和初始心跳。
4. Worker 按准备、拉取、校验、入库、缓存刷新阶段报告真实进度。
5. Python 进程通过 `runForJob` 注册到任务，支持强制终止。
6. Provider 响应通过协议校验和模块质量门。
7. 数据事务提交后刷新缓存。
8. 只有 Provider 成功、质量门通过且事务提交完成，任务才能写入 `SUCCESS`。
9. `finally` 停止 watchdog、注销进程并释放模块锁。

手动、自动和登录补偿严格共用以上生命周期。

## 7. 状态与取消

合法状态流转：

```text
QUEUED -> RUNNING -> SUCCESS
                  -> PARTIAL_FAILED
                  -> FAILED
                  -> CANCELLING -> CANCELLED
                  -> INTERRUPTED
```

- 取消接口幂等。
- 取消先持久化 `cancelRequested`，再终止已注册 Python 进程。
- Worker 在阶段边界及批处理循环中检查取消标志。
- `CANCELLED`、`FAILED/LOCK_LOST` 等受保护终态不能被后续成功或通用异常覆盖。
- watchdog 续期失败确认锁丢失后，终止任务进程并写入 `FAILED/LOCK_LOST`。
- 服务重启后，心跳过期活动任务标记 `INTERRUPTED`，由后续调度、登录补偿或管理员重新触发。

## 8. 自动调度迁移

- 新闻、今日比赛、季后赛、选秀、历史赛季以及自动全量任务全部改为向 Coordinator 提交。
- 每天 3:00 的自动全量任务创建 `FULL_SYNC / SCHEDULED` 父任务。
- 新闻去重等维护型任务保留独立调度，不进入数据同步任务模型。
- 自动调度与手动按钮从同一个 `SyncDefinitionRegistry` 获取模块定义，避免参数漂移。

## 9. 管理员登录补偿

### 9.1 触发方式

管理员认证成功后发布 `AdminLoginEvent`。登录响应不等待补偿检查或同步任务执行。

`SyncCatchupService` 异步处理事件，并通过跨实例互斥和冷却窗口避免多个管理员同时登录造成重复检查。

### 9.2 判定规则

对每个同步定义计算最近一次应执行时间：

- 若最后成功时间早于最近一次应执行时间，则需要补偿。
- 若没有成功记录，则视为需要补偿。
- 若模块已有活动任务，则去重。
- 同一模块错过多个周期只补跑一次，不逐次回放。
- 时间计算统一使用 `Asia/Shanghai`。

若停机期间错过自动全量任务，则创建一次 `FULL_SYNC / LOGIN_CATCHUP`。若此时存在普通活动任务，补偿检查保持待处理并按配置的重试间隔重新检查；活动任务结束后再创建全量任务，不绕过全量独占规则，也不要求管理员再次登录。该任务与普通全量任务使用相同步骤顺序和失败继续规则。

### 9.3 可见性

登录补偿任务进入统一任务历史，来源显示为“登录补偿”，支持查看、取消和失败后单模块重试。

## 10. API 契约

### 10.1 提交模块任务

`POST /api/admin/sync/{module}`

- 创建新任务：HTTP `202`，`reused=false`。
- 复用活动任务：HTTP `200`，返回原 `jobId`、真实 `triggerType`，`reused=true`。

### 10.2 提交全量任务

`POST /api/admin/sync/full`

- 创建成功：HTTP `202`。
- 存在普通活动任务：HTTP `409`，响应包含冲突模块。

### 10.3 取消任务

`POST /api/admin/jobs/{id}/cancel`

幂等返回是否接受取消及任务当前状态。终态任务返回 `accepted=false`，不改写终态。

### 10.4 查询

- `GET /api/admin/sync/overview` 返回模块数据量、最后成功记录、活动任务以及活动全量步骤。
- `GET /api/admin/jobs` 支持按模块、来源、状态和时间分页筛选。
- `GET /api/admin/jobs/{id}` 返回任务详情；全量任务同时返回步骤列表。

## 11. 管理中心交互

- 模块卡片显示数据总量、最后成功时间、当前任务状态、真实进度和阶段。
- 活动任务显示来源、开始时间和已运行时长。
- 点击已有活动任务的模块按钮时关联现有任务，不制造第二个任务。
- 活动任务统一显示取消操作；终态后恢复同步按钮。
- 全量同步显示当前模块、总体进度、已完成模块数和最终模块汇总。
- 失败模块提供独立重试。
- 任务历史持久化展示，支持模块、来源和状态筛选，刷新页面后可恢复。
- 明确区分“最后尝试”和“最后成功”，失败任务不能更新最后成功时间。

## 12. 错误与质量门

- Provider 全失败：`FAILED/PROVIDER_FAILED`。
- Provider 成功但合法无数据：按模块契约判定成功或部分失败。
- Provider 状态与数据数组不一致：`FAILED/PROTOCOL_ERROR`。
- 质量门不通过：`FAILED` 或 `PARTIAL_FAILED`，不得写成功时间。
- Python 超时：`FAILED/PYTHON_TIMEOUT`，错误消息使用实际配置值。
- 数据库事务失败：`FAILED/DB_ERROR`。
- 锁丢失：`FAILED/LOCK_LOST`。
- 用户取消：`CANCELLED/CANCELLED`。

全量父任务保留每个失败步骤的原始错误码和消息。

## 13. 测试策略

### 13.1 单元测试

- 自动、手动和登录补偿解析到同一个 Worker 与定义。
- 同模块活动任务复用和自动去重。
- 普通任务并发、全量独占和冲突模块响应。
- 全量步骤失败后继续执行及父任务汇总。
- 取消、进程终止、锁丢失和终态保护。
- Provider 状态协议及模块质量门。
- 登录补偿的错过一次、错过多次折叠、无需补偿、首次部署、并发登录和时区边界。

### 13.2 集成测试

- 所有数据型 `@Scheduled` 方法只提交 Coordinator，不直接调用业务 Service。
- 管理员登录响应不被补偿任务阻塞。
- 任务记录、步骤、心跳和最后成功时间事务一致。
- 重启恢复将过期任务标记为 `INTERRUPTED`。

### 13.3 Playwright 验收

- 手动提交并完成一个模块同步，验证对应业务页面数据更新。
- 手动点击正在运行的自动任务并关联现有进度。
- 取消自动任务，终态后重新手动同步。
- 全量任务单模块失败后继续并显示部分失败汇总。
- 按来源和状态筛选任务历史。
- 刷新页面后恢复活动任务。
- 管理员登录触发遗漏任务，登录不阻塞且补偿任务可见。

## 14. 验收标准

- 同一模块无论由 `SCHEDULED`、`MANUAL` 还是 `LOGIN_CATCHUP` 触发，执行同一 Worker 并产生一致的数据结果和状态判定。
- 自动任务和登录补偿任务在管理中心可见、可取消。
- 手动点击活动模块不创建重复任务。
- 系统停机错过调度后，管理员首次登录会异步补跑最近遗漏任务。
- 全量任务中单模块失败不阻断后续模块。
- 失败、取消、锁丢失或协议错误不会更新模块最后成功时间。
- 后端完整测试、前端构建和 Playwright 核心流程全部通过。
