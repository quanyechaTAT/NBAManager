# 新闻同步性能、覆盖率与 100 条保留策略设计

## 背景

当前新闻同步存在三个相互关联的问题：管理员感知手动同步较慢、自动同步在最近两天新增资讯偏少、`game_news` 未稳定保持在预期的 100 条以内。

生产数据表明，成功的 `NEWS` 手动任务平均耗时约 25.4 秒，定时任务平均约 33.8 秒，因此后端手动执行本身并不比自动执行慢。主要性能成本来自 Python 在 Java 入库查重前翻译整批候选，以及 Java 对每条候选执行多次查询和单条保存。数据覆盖不足的直接原因是 ESPN JSON 当前只返回 50 条，其中仅 18 条属于 `Story` 或 `HeadlineNews`，重复同步通常新增 0 条。

## 目标

1. 手动、定时和管理员登录补偿使用完全相同的新闻同步执行逻辑与质量门。
2. 聚合多个可靠新闻源，优先覆盖最近 48 小时的 NBA 资讯。
3. 在翻译和写库前完成候选规范化与批量去重，只处理新增或确实需要更新的资讯。
4. `game_news` 全部类型合计最多保留最新 100 条，不按分类分别计算。
5. Provider 部分失败时保留成功来源的结果；所有来源失败时任务失败，不把失败误报为“0 条成功”。

## 非目标

- 不改变比赛、球员、球队等其他同步模块的数据源。
- 不改变新闻详情、收藏和浏览历史的前端交互。
- 不为了凑满 100 条而生成、复制或伪造资讯；100 是保留上限，实际数量取决于真实来源。
- 不提高模块并发度去绕过外部 API 延迟，以免触发供应商限流。

## 方案

### Provider 聚合

Python 新闻抓取器聚合三个来源：

- ESPN JSON：保留 `Story` 和 `HeadlineNews`。
- ESPN NBA RSS：补足 JSON 列表可能遗漏的文章。
- CBS Sports NBA RSS：提供第二个独立来源。

每个 Provider 返回统一候选字段和独立状态：`provider`、`succeeded`、`items`、`error`。候选按规范化后的 `sourceUrl` 去重；缺少 URL 时回退到规范化标题。合并结果按发布时间倒序，优先保留最近 48 小时，再用更早的真实资讯补足本轮数量上限。

当至少一个 Provider 成功且有候选时，`newsSourceStatus=ok`；至少一个 Provider 成功但没有候选时为 `empty`；全部失败时为 `failed`。

### 增量处理和翻译

Provider 抓取和候选标准化不执行翻译。Java 在获取候选后，一次性查询候选 URL 和标题对应的现有记录，将候选分为：

- 已存在且无需更新：跳过翻译和保存。
- 已存在但缺少中文字段或图片等可补充字段：进入更新集合。
- 全新资讯：进入新增集合。

仅对新增和需要更新的候选执行批量翻译。翻译失败时保留英文原文和 `titleEn/contentEn`，任务仍可部分成功，后续 `TRANSLATION` 模块负责补偿。新增和更新记录分别使用批量保存，避免逐条 N+1 查询。

为控制单轮耗时，单次同步最多处理 40 条合并候选。该数量可通过配置覆盖，但不在前端开放设置。

### 统一任务入口

`NEWS` 的手动、定时、登录补偿都继续通过 `SyncCoordinator -> NewsSyncWorker` 执行，不保留第二套直接刷新实现。新闻页面的管理员“刷新”动作提交统一任务并根据 `jobId` 查询真实状态，不再固定等待 10 秒后猜测是否完成。

任务进度按阶段更新：

1. `FETCHING`：拉取 Provider。
2. `DEDUPLICATING`：批量识别新增/更新候选。
3. `TRANSLATING`：翻译需要处理的候选。
4. `PERSISTING`：批量写入并执行保留策略。

### 100 条保留策略

`game_news` 的所有分类共用一个上限：100 条。同步成功写入后，在同一业务流程中按 `createTime DESC, id DESC` 保留最新 100 条，删除其余记录。

删除旧资讯前先批量清理对应的新闻收藏和浏览历史，避免逐条删除和外键残留。赛事、夏季联赛、普通新闻、交易、伤病、选秀等类型全部计入 100 条。

手工新增资讯也执行相同上限，避免只有自动同步才会清理。更新现有资讯不改变原 `createTime`，不会因为编辑而挤掉真正的新资讯。

## 错误处理

- 单一 Provider 失败：记录 Provider 失败详情，继续使用其他来源，任务可成功。
- 全部 Provider 失败：返回 `PROVIDER_FAILED`，不执行清理，保留现有 100 条数据。
- 翻译失败：保留英文内容，计入跳过/待翻译数量，不回滚已经成功抓取的真实资讯。
- 批量写入失败：事务回滚本轮写入和清理，任务返回 `PERSIST_FAILED`。
- 清理失败：事务回滚，避免出现写入成功但旧数据未清理导致长期超过 100 条。

## 测试设计

### Python 契约测试

- ESPN JSON、ESPN RSS、CBS RSS 合并并按 URL 去重。
- 最近 48 小时优先，结果按发布时间倒序。
- 一个 Provider 成功、其他失败时返回 `ok`。
- 全部 Provider 失败时返回 `failed`。
- 缺 URL 的候选按规范化标题去重。

### Java 服务测试

- 批量查重只保存新增和需要补充的记录。
- 已存在候选不进入翻译集合。
- Provider 全失败时不清理现有数据。
- 写入 100 条以上后仅保留最新 100 条，所有分类统一计数。
- 删除旧记录时同步清理收藏和浏览历史。
- 手工创建第 101 条资讯后仍保留 100 条。

### 任务和前端验收

- `MANUAL`、`SCHEDULED`、`LOGIN_CATCHUP` 的 `NEWS` 任务调用同一 Worker。
- 新闻页面刷新后显示真实任务进度和终态。
- 真实同步后验证 Provider 结果、抓取数、新增数、总数不超过 100。
- 对比优化前后任务耗时，并确认重复同步不会重复翻译和写入。

## 验收标准

1. 完整后端、前端和 Python 测试通过。
2. 任意同步完成后 `game_news` 总数不超过 100。
3. 至少一个 Provider 可用时不会因其他 Provider 失败而丢失全部结果。
4. 连续执行两次新闻同步，第二次对重复候选不执行翻译和插入。
5. 数据管理中心和新闻页面均能显示真实任务状态，不以固定等待时间判断完成。
